Architecture and handover

Deal Rescue

Deterministic code picks the deals worth reviewing. Two agents work out why each one is stuck and what to do about it. Deterministic code checks their output. A person approves anything that leaves the system.

1. What it does

A seller with sixty open opportunities can't inspect them all every week.

CRM fields tell you a deal looks stale. Time in stage, days since contact, a close date that keeps moving. They don't tell you why it's stuck, and why is what decides your next move. A deal stalled because procurement was never engaged and a deal stalled because the champion left look identical in the structured data. They need opposite responses.

Deal Rescue answers one question: which deals need attention this week, why, and what should I do about it. Every answer can be checked line by line.

How it runs

Data arrives as a scheduled CRM export in a Cloud Storage bucket. One module maps the Salesforce schema to an internal one and records when the extract was taken. The age of that snapshot is an input the system uses, not something it assumes away.

Then plain Python scores every open deal against eight rules. Time in stage versus the median for that stage on deals we won. Days since the customer last engaged. Champion silence. Close date slips. Amount erosion. Stage regression. Single threading. Imminent close with nothing booked.

Each rule reports its numerator, denominator, threshold, and a plain explanation. Scores get weighted by severity, ranked, and capped. Same snapshot, same deals, same order, every run. No model has touched anything yet.

Only then do the agents run. The first one gets the deal plus its already-computed signals, told those numbers are facts it can't recompute. It reads the seller's notes, the activity timeline, and the contact map. It returns one root cause with cited evidence, the facts that argue against that conclusion, what it doesn't know, and a confidence level.

The second agent takes that validated investigation, not the raw notes, and picks exactly one next action from a closed set. If the action is customer-facing, it drafts the message.

Then Python checks the output. Eight checks, six of them blocking. Cited IDs have to resolve to real records. A signal that didn't trigger can't support a risk claim. No number can appear in a customer-facing email unless it appears in the source material the model was given. Nothing reaches a person until it passes. Nothing leaves the system until a person approves it.

Three things worth knowing

Triage is reproducible, and you can prove it with no model running at all.

Every claim in a generated assessment resolves to a record you can open.

When a stage fails, it says so and degrades. It never fills the gap with something invented.

Scope. This is decision support. It doesn't block anyone, contact customers, send mail, or change opportunity records. A high-risk result is evidence for a human to review, not a verdict. Every proposed action comes back pending approval.

2. The rule that shapes everything

The model isn't allowed to count.

That's the whole design. Every decision below follows from it.

JobWho does itWhy
Counting, date math, thresholds, rankingSQL and PythonOne answer is correct. A model can only add variance.
Reading notes, reconciling them with the numbers, picking an action, writing the emailModelNo closed-form answer. It's reading comprehension and judgment.
Checking the model's outputPythonGrading a generator with another generator gets you confident nonsense.
Approving anything customer-facingA personIt's someone's customer and someone's quota.

This is testable, not just asserted. make run-deterministic runs the whole triage with zero model calls.

I built an earlier version that fed hundreds of CRM rows straight into a model and asked which deals were at risk. Same inputs, different deal counts on different runs. The mistake was asking one component to be the database and the reasoner at the same time.

3. The pipeline

Order is fixed in code. No model decides what runs next. The stripe shows who does the work.

Deterministic Model Human
3.1Load the exportPython

Six CSVs land in a Cloud Storage bucket on the Salesforce object schema: Opportunity, Account, Contact, Task, ContentNote, OpportunityFieldHistory. An export manifest records the extract timestamp and row counts.

One module knows the Salesforce field names and maps them to the internal schema. It drops every column the pipeline doesn't use. When the export changes shape, one file changes and nothing else cares.

Batch, not live API reads. Three reasons: it keeps load off the CRM org, it takes API rate limits out of the critical path, and it makes every run reproducible against a known snapshot. That last one is what makes the deterministic layer testable at all.

3.2Work out how stale the data isPython

The manifest loads with the data, so every downstream component knows the snapshot's age.

This matters more than it sounds. Six of the eight rules count days, and three of them infer risk from a record not being there. Those three break on a stale extract: a customer reply that landed after the export looks exactly like no reply at all.

So any silence-based signal the lag alone could explain gets marked provisional, with the math shown:

CHAMPION_SILENT. Measured 24 days against a 3-day-old export. A reply after the extract would put this under the 21-day threshold.

A provisional signal still counts toward the score. It's a caveat on the claim, not a reason to throw out evidence, and the investigating agent is told to record the caveat instead of asserting the finding. Rules that read a value that's actually there (amount erosion, stage regression, close date slips) never get marked, because export lag can't invent them.

3.3Score every open dealPython

Eight rules, all arithmetic on structured fields. This module never reads note text. A test enforces that.

RuleWhat it measuresSeverity
STAGE_STALLDays in current stage vs. the median for that stage on won dealsCritical
NO_CONTACTDays since the customer engaged. Outbound doesn't count.High
CHAMPION_SILENTDays since the named primary contact specifically engagedHigh
CLOSE_DATE_SLIPHow many times the forecast date movedHigh
AMOUNT_EROSIONDrop from the original amountCritical
STAGE_REGRESSIONDeal moved backwardsCritical
SINGLE_THREADEDOne engaged contact above a configured deal sizeMedium
IMMINENT_CLOSE_NO_MEETINGClose date near, nothing on the calendarHigh

The stage benchmark comes from won deals on purpose. It answers the useful question: how long does this stage take when things are going well.

Every rule reports its numerator, denominator, threshold, and a plain explanation. A signal an analyst can't check independently is a signal they can't act on.

Thresholds live in one config file and are the only tuning surface. They're reasoned starting points, not calibrated numbers. Calibrate them against closed outcomes over a quarter before treating the bands as authoritative.

3.4Pick the review setPython

Severity-weighted scores produce four bands (critical, at risk, watch, healthy) plus a separate INSUFFICIENT_HISTORY band for deals too new to judge. "We can't tell yet" and "we checked and it's fine" are different answers and they're reported differently.

Deals get ranked and capped. Ties break on amount, then ID, so the same snapshot always produces the same set in the same order.

The cap is a config value and it's what bounds model spend. The expensive stage only ever sees a handful of deals.

Still no model has run.

3.5InvestigateModel

The first agent gets the deal and its computed signals, with those numbers declared as facts it can't recompute. It has three read-only tools: seller notes, the activity timeline with direction, and the account contacts with engagement status.

It returns a schema-enforced object. One root cause, evidence claims with citations, contradicting evidence, unknowns, confidence. Contradicting evidence and unknowns are required fields, not optional ones. Confident output with no recorded counterevidence is a reason to distrust it.

This is where the model earns its cost. Scoring can prove a deal has been in negotiation well past its benchmark and the primary contact went quiet. It can't read "she mentioned she's moving to a new role and someone from the platform team will pick this up" and recognize an unmanaged champion transition. That reconciliation is the job.

3.6Pick an actionModel

The second agent takes the validated investigation, not the raw notes, and proposes exactly one action from a closed set.

ActionDirectionDraft required
EMAIL_CONTACTCustomer-facingYes
MULTITHREADCustomer-facingYes
SCHEDULE_MEETINGCustomer-facingYes
ESCALATEInternal, to sales leadershipNo
DISQUALIFYInternal, stop working itNo

It's explicitly told not to default to another email. When the evidence shows no budget, no identified buyer, and nothing forcing a decision, the right answer is disqualify, and saying so is the service. Restricting this agent to the validated investigation stops it re-interpreting evidence that already passed checks.

3.7VerifyPython

Eight checks run against the model output. No model involved.

Blocking: fabricated signal, note, or activity IDs. Citing a signal that didn't trigger. Any number in customer-facing text that isn't in the source material. An uncited claim. Deal ID mismatch. A customer-facing action with no draft.

Advisory: a number in internal reasoning that isn't sourced, which usually means the model counted (that belongs in 3.3). Missing counterevidence or unknowns.

The source corpus is everything the tools could return for that deal, so a number the model didn't read is a number it produced.

The checks run against generated prose, not just structured fields. The structured fields are built in code and can't lie. The prose is what a human reads and acts on, so that's where a bad number does damage. I've seen a system whose integrity gate validated IDs on a code-built object while the generated narrative went unchecked, and whose published metrics didn't match its own stored records.

3.8Fail predictablyPython

A source that can't be read reports that, with an explicit note that missing records aren't evidence. Model errors get one retry if transient, none if they look like a real bug. Malformed output gets one repair attempt with the validation error handed back.

A failed investigation returns FAILED with the deterministic signals intact. A failed action stage returns PARTIAL with the investigation intact. Passing verification on an unreadable source gets downgraded to PARTIAL, because passing the checks isn't the same as having seen the evidence.

A missing perspective is never replaced with an invented one.

3.9ApproveHuman

The whole package gets presented: diagnosis, evidence, draft message, proposed record changes, verification status. A proposal with a blocking failure can't be approved.

Approved actions go to an outbound queue. Nothing is sent and no record is changed by the system in this release.

5. Security

Note text, activity subjects, and account fields come from outside the system. They're treated as untrusted all the way through.

Agent instructions are static constants. No retrieved text ever gets interpolated into an instruction, and that's asserted by a test, not by convention. Untrusted content only reaches a model as tool output.

Model Armor, three boundaries

BoundaryWhat happensWhy
Inbound seller requestblockUntrusted input at the edge
Retrieved note textflag onlySee below
Outbound customer emailblockThe only text that leaves

The middle one is on purpose.

A note with an injection in it also has real evidence in it. "Sent proposal, no response" can sit in the same record as "ignore all previous instructions." Blocking the record throws away the evidence to avoid the instruction. The architecture already keeps retrieved text in the data channel, so screening here is defense in depth, not the control. It flags, and the reviewer sees the flag.

Tested against a seeded adversarial record. The injection matches the prompt-injection classifier at high confidence, a clean draft returns no match, and the agent still pulls the record's real evidence and cites it.

Memory scope

Memory shapes the recommendation. It never shapes the diagnosis.

The investigation has to stay traceable to the current snapshot. That's what makes deterministic verification possible. A recalled claim isn't a fabricated ID the gate can resolve, it's prose from a previous session with nothing to check it against.

So memory is wired to the action stage only. It carries what the seller already decided and what they've said they prefer, not risk assessments, and it's rendered into the prompt under a heading that says it can't be cited as evidence.

Durable records that need audit trails and tenant scoping belong in the case store. This is the soft recall half only. A remembered risk label is not current evidence.

7. Evals

Three tiers, reported separately. I don't average them into one number.

TierMethodStanding
1, deterministicSelection order, bands, which rules fire. One correct answer.release gate
2, mechanicalCitations resolve, action in allowed set, uncited claimsregression check
3, managed autoraterGroundedness, action appropriateness, uncertainty handlingadvisory

Tier 1 is a real pass or fail. The deterministic layer has one correct output and any deviation blocks the release.

Tier 3 uses the managed evaluation service instead of a judge I'd have to write and maintain myself.

Rubric governance

Custom rubrics are versioned, and the version is recorded with every score so results never get compared across revisions.

Each rubric has anchor cases you can run on demand. Against identical evidence, a correct disqualification scores 5, another follow-up email scores 1, and a fabricated approval claim scores 1. A rubric nobody has run against a known-bad answer is a rubric that might return 5 for anything.

The managed groundedness metric isn't deterministic. The same diagnosis scored 0 and then 1 on consecutive runs, minutes apart. It's a binary judgment made by a model, and it's strict about literal attribution: it'll say a role word isn't supported when the evidence only names the person. Don't gate a release on its average without a human checking, and I don't report one anywhere.

10. Cost

Two things drive spend.

The hosted runtime bills continuously while provisioned. It doesn't scale to zero, and it's the bigger line item.

Model inference bills per call and is bounded by architecture, not by convention. Deterministic selection runs first and caps how many deals ever reach a model, at roughly 6,500 tokens per deal reviewed. Growing the opportunity population doesn't grow model cost, because the expensive stage only ever sees the capped set.

Screening and evals bill per call. At review volumes that's pennies. Storage and analytics are noise.

A billing budget with staged alerts is configured on the project.

11. What I'd fix before you trust it with real writes

These are deliberate boundaries for this release, in the order I'd tackle them.

  1. Approval capture in Gemini Enterprise. Approval is real at the operator interface. In the chat surface a proposal comes back pending with nothing to record the decision. Until there's a capture path, treat the chat surface as read-only and record approvals through the operator interface.
  2. Read-back after writes. Nothing confirms state in a system of record after a write, because nothing writes to one yet. Any write path needs read-back with it. A successful API call isn't a completed workflow.
  3. Telemetry from the hosted runtime. Confirmed working from the operator interface, not landing from Agent Engine. IAM and config propagation are ruled out. Sandbox egress is the open question.
  4. Tenant and entitlement model. There's no per-seller entitlement enforcement. Multi-seller rollout needs that first.
  5. Currency and time zones. Amounts are single currency, dates are calendar dates. Multi-region needs currency on the amount fields and tenant-aware day boundaries, because "14 days since contact" is ambiguous across zones.
  6. Threshold calibration. Current thresholds are reasoned, not derived. Calibrate against closed outcomes over a quarter before treating bands as authoritative.
  7. Eval corpus. The current scenario set exercises behavior. It's not big enough to support an accuracy claim. That needs a labeled corpus with analyst adjudication.
On numbers. There's no accuracy, efficiency, or financial impact claim anywhere in this document or in the system's reporting. Operational metrics are generated from captured execution data, and anything not captured says so.

12. Questions you'll ask

Architecture

Why two agents instead of one?

I measured it. Same cases, same tools, same verifier: a single agent matched the two-agent version on every dimension I could score objectively, at about two-thirds the cost. I kept the split so the drafting prompt can change without touching the diagnosis prompt. That's a maintainability argument, not a quality one, and I wouldn't defend it as a quality win on what I have.

Is this a multi-agent system?

Two by count, three if you include the router on the chat surface. But I wouldn't call it multi-agent, and I don't anywhere in this doc.

There's no delegation and no negotiation. It's a fixed sequence: one agent produces a typed object, the next consumes it. The handoff is a Pydantic model, not a conversation. Calling that multi-agent oversells it.

What would make it genuinely multi-agent is parallel specialists with different views of the evidence and a reconciliation step. I considered that and rejected it. Splitting by data type means one agent sees numbers and the other sees notes, and then neither can catch mild numbers contradicting alarming notes, which is the case that justifies using a model at all.

Why is selection deterministic?

Because it's arithmetic, and a model doing arithmetic adds variance without adding capability. My earlier version fed CRM rows straight to a model and got different deal counts from identical inputs. One component was being asked to be the data layer and the reasoning layer at once.

Is the output reproducible?

Triage is. Same snapshot, same deals, same order, and I can show it with no model running. The recommended action isn't, because it's a judgment call with more than one defensible answer. That's the boundary working. It's also why the action set is closed and the output gets verified.

There's a model in the entry path on the chat surface. Doesn't that break the determinism claim?

Fair question. The entry agent routes and presents. It can't score a deal, change the review set, or skip verification, because those run in fixed order inside the tool it calls. But there is a model in the path and I'd rather say that than let it slide.

Correctness

How do you stop it fabricating?

Eight deterministic checks after generation, six blocking. The one that matters most: no number can appear in customer-facing text unless it's in the source material the model was given. The source corpus is everything the tools could return for that deal, so a number the model didn't read is a number it made up.

Why check the prose instead of the structured output?

The structured fields are built in code and can't fabricate. The prose is what a human reads and acts on. A gate that only validates the safe artifact gives you assurance without protection. I've seen that exact failure: a system whose integrity gate validated IDs on a code-built object while the generated narrative went unchecked, and whose published numbers didn't match its own stored records.

What stops a well-sourced but wrong conclusion?

Nothing, fully. The gate catches fabricated citations and unsourced numbers. It can't catch a conclusion that's correctly attributed and still wrong, like a misread of tone or a causal story the evidence only permits. That's why human approval is mandatory and why counterevidence and unknowns are required fields.

It cited the record with the injection in it. Is that a control failure?

No, that's correct. The record has an injection attempt and real facts in the same body. Treating untrusted text as data means taking the facts and ignoring the instruction. Refusing to read it would discard evidence, which is worse.

Data and ops

Why batch instead of live API reads?

Keeps load off the CRM org, takes rate limits out of the critical path, and makes every run reproducible against a known snapshot. It also forces freshness to be explicit: the extract timestamp is an input, and day-counting rules get qualified against it.

What happens when a source is down?

It degrades in three layers, each with tests that inject the failure. An unreadable source reports that, with an explicit note that missing records aren't evidence. Model errors get one retry if transient, none if they look like a bug. A failed stage downgrades the result and names what failed. No stage output ever gets replaced with generated content.

How does this scale?

The deterministic layer is relational and moves to the warehouse the export already lands in. The model stage is the constrained resource and it's capped by design, since selection runs first. More opportunities means more warehouse cost, not more model cost.

How do we operate it?

Thresholds, the cap, and the staleness tolerance are config in one module, effective next run. The regression suite is hermetic so it gates changes without model quota. Every run is correlated end to end by one ID, and reports are generated from captured data, not written by hand.

Governance

Where does memory get used, and where doesn't it?

It carries what the seller already decided and what they prefer, and it reaches the action stage only. It's kept out of the diagnosis on purpose: the investigation has to stay traceable to the current snapshot or verification has nothing to resolve a recalled claim against. Durable records that need audit trails go in the case store. A remembered risk label is not current evidence.

Why Model Armor and not the agent security tooling?

Placement and cost. Model Armor screens the three boundaries this system actually has, with a different response at each. The security dashboard runs through Security Command Center, whose paid tiers are an org-level commitment and out of proportion to one workload. Screening is also defense in depth here, not the primary control. Keeping untrusted text in the data channel is the control.

The agents scored 5 out of 5 on the rubrics. Should we be skeptical?

Yes, and that's why the anchors exist. Against identical evidence the same rubric gives a 1 to a redundant follow-up and a 1 to a fabricated approval claim. That shows the rubric discriminates, which makes a 5 a result instead of an artifact. Separately, the managed groundedness metric disagreed with itself between two runs, so I don't report its mean anywhere.

What's the weakest part?

The eval corpus. It exercises behavior but it's not big enough to tell two architectures apart or support an accuracy claim. I know that because the architecture comparison I ran came back inconclusive. Second is approval capture in the chat surface.

What did you decide not to build?

One rule: nothing goes in because the platform supports it. Autonomous writes, tenant modeling, a custom UI, RAG, and forecasting were all scoped out on purpose, and each is recorded as a boundary, not an oversight. Same rule applied to managed services. I evaluated one and didn't use it based on its own docs.

Deal Rescue. Deterministic triage, bounded model reasoning, deterministic verification, human approval. Operational figures come from captured execution data.
