Solution architecture & operational handover

Deal Rescue

An analyst-grade pipeline review system. Deterministic code identifies the opportunities that merit investigation; bounded model reasoning explains why each is stuck and proposes a next action; deterministic verification and human approval govern everything that leaves the system.

Status

1. What this system is for

A seller carrying sixty open opportunities cannot deeply inspect them every week. Structured CRM fields can show that a deal looks stale; they cannot explain why it is stuck, and the why is what determines the next action.

Deal Rescue answers one question — which deals need attention this week, why, and what should I do next? — and returns an analyst-style assessment: the deal, the evidence behind the diagnosis, the counterevidence, a recommended next action, a grounded customer follow-up draft, and a proposed CRM update. Every one of those arrives as a proposal pending human approval.

Scope boundary. This release is decision support. It does not block, contact customers, send mail, or change opportunity records. A high-risk finding is evidence requiring review, not a determination.

2. The governing principle

The model is not permitted to count.

The architecture is organised around one boundary, and every design decision below follows from it.

ConcernOwnerRationale
Counting, date arithmetic, thresholds, rankingSQL and PythonExactly one answer is correct. A model can only introduce variance.
Interpreting notes, reconciling them with the metrics, selecting an action, drafting copyModelNo closed-form answer exists. The task is reading comprehension and judgement.
Validating the model's outputPythonGrading a generator with another generator produces confident error.
Authorising anything customer-facingA personIt is a customer relationship and a quota.

This is verifiable rather than asserted. make run-deterministic executes the complete triage — every open opportunity scored, ranked and selected — with no model invocation at all.

3. Pipeline

Execution order is fixed in code. It is not a routing decision delegated to a model. The stripe on each stage indicates which component performs the work.

Deterministic Model Human
3.1Ingest the CRM exportDeterministic

Opportunity data arrives as a scheduled Salesforce extract landing in a Cloud Storage bucket: six CSV objects on the Salesforce object schema — Opportunity, Account, Contact, Task, ContentNote, OpportunityFieldHistory — accompanied by an export manifest recording the extract timestamp and row counts.

A single normalisation module owns the mapping from Salesforce API field names to the internal schema, and discards every column the pipeline does not consume. When the export changes shape, one file changes and no rule, prompt or agent is affected.

Batch ingestion is a deliberate choice over live API reads: it bounds load on the CRM org, makes every run reproducible against a known snapshot, and removes API rate limits from the critical path.

3.2Establish data freshnessDeterministic

The export manifest is loaded alongside the data, so the snapshot's age is available to every downstream component. This matters more than it first appears: six of the eight risk rules count elapsed days, and three of them infer risk from the absence of a record.

Those three are vulnerable to extract lag — a customer reply landing after the extract is indistinguishable from no reply at all. Any silence-derived signal that the lag alone could account for is therefore marked provisional, with the arithmetic stated in the output:

CHAMPION_SILENT — measured 24 days against a 3-day-old extract. A reply after the extract would place this below the 21-day threshold.

A provisional signal still contributes to the risk score. It is a qualification on the claim, not grounds to discard evidence, and the investigating agent is instructed to record the caveat rather than assert the finding. Signals that read a value which is present — amount erosion, stage regression, close-date movement — are never marked, because extract lag cannot manufacture them.

3.3Score every open opportunityDeterministic

Eight rules evaluate against structured fields only. This module never reads note text; the separation is enforced by test.

RuleMeasuresSeverity
STAGE_STALLDays in current stage vs. the median for that stage across won opportunitiesCritical
NO_CONTACTDays since the customer last engaged; outbound activity does not countHigh
CHAMPION_SILENTDays since the named primary contact specifically engagedHigh
CLOSE_DATE_SLIPCount of forecast date revisionsHigh
AMOUNT_EROSIONProportional reduction from the original amountCritical
STAGE_REGRESSIONBackwards movement through the pipelineCritical
SINGLE_THREADEDOne engaged contact above a configured deal sizeMedium
IMMINENT_CLOSE_NO_MEETINGNear-term close date with no scheduled conversationHigh

The stage-duration benchmark is derived from won opportunities, which answers the operationally meaningful question: how long does this stage take when the deal is progressing. Every rule records its numerator, denominator, threshold and a plain-language explanation, because a signal an analyst cannot check independently is a signal they cannot act on.

Thresholds are configuration, held in one file, and are the only tuning surface. They are starting positions for this deployment and should be calibrated against closed outcomes during the first operating quarter.

3.4Select the review setDeterministic

Severity-weighted scores produce four bands — critical, at risk, watch, healthy — plus a distinct INSUFFICIENT_HISTORY band for opportunities too new to judge. Keeping "we cannot yet tell" separate from "we checked and it is fine" is a deliberate reporting decision.

Opportunities are ranked and capped. Ties resolve on amount, then identifier, so a given snapshot always produces the same review set in the same order. The cap is a configuration value and bounds model spend per run: the expensive stage only ever sees a small set.

No model has executed at this point.

3.5InvestigateModel

The investigating agent receives the opportunity and its already-computed signals, with those values declared as established facts it may not recompute. It is granted three read-only tools: seller notes, the activity timeline including direction, and the account contact map with engagement status.

It returns a schema-enforced object: a single root cause, evidence claims each carrying citations, contradicting evidence, unknowns, and a confidence level. Contradicting evidence and unknowns are required fields rather than optional ones — confident output with no recorded counterevidence is treated as a signal to distrust it.

This is where model reasoning earns its cost. Deterministic scoring can establish that an opportunity has been in negotiation well past its benchmark and that the primary contact has gone quiet. It cannot read "she mentioned she is moving to a new role and someone from the platform team will pick this up" and recognise an unmanaged champion transition. That reconciliation of quantitative signal against written record is the task.

3.6Propose an actionModel

A second agent consumes the validated investigation — not the raw notes — and proposes exactly one next action from a closed set. Three actions are customer-facing and require a drafted message; two are internal and do not.

ActionDirectionDraft required
EMAIL_CONTACTCustomer-facingYes
MULTITHREADCustomer-facingYes
SCHEDULE_MEETINGCustomer-facingYes
ESCALATEInternal — sales leadershipNo
DISQUALIFYInternal — cease workNo

The agent is explicitly instructed against defaulting to further outreach. Where the evidence establishes no budget, no identified economic buyer and no compelling event, the correct output is disqualification, and the service rendered to the seller is saying so. Restricting this agent to the validated investigation prevents it from re-interpreting evidence that has already been checked.

3.7VerifyDeterministic

Eight checks execute against the model output. No model participates in this stage.

Blocking. Fabricated signal, note or activity identifiers. Citation of a signal that did not trigger. Any quantity in customer-facing text absent from the source material. An uncited claim. Opportunity identity mismatch. A customer-facing action with no draft.

Advisory. A quantity in internal reasoning absent from the source — which may indicate the model counted, an operation that belongs in stage 3.3. Missing counterevidence or unknowns.

The source corpus is the union of everything the tools can return for that opportunity, so a quantity the model did not read is a quantity it produced. The check is applied to generated prose, not only to structured fields — the prose is what a human reads and act on, and is therefore where an unsupported figure does damage.

3.8Degrade predictablyDeterministic

Sources that cannot be read report their state rather than raising, and carry an explicit instruction that absent records must not be treated as evidence. Model errors receive one retry when transient and none when they indicate a defect; malformed output receives one repair attempt with the validation error supplied.

A failed investigation returns FAILED with the deterministic signals intact. A failed action stage returns PARTIAL with the investigation intact. A result that passes verification but rests on an unreadable source is downgraded to PARTIAL, because passing the checks is not the same as having seen the evidence.

A missing perspective is never substituted with an invented one.

3.9AuthoriseHuman

The assembled proposal — diagnosis, evidence, draft message, proposed record changes, verification status — is presented for explicit approval. A proposal with a blocking verification failure cannot be approved. Approved actions are written to an outbound queue for execution; no record is mutated and no message is transmitted by the system itself in this release.

5. Security and trust boundaries

Note text, activity subjects and account fields originate outside the system and are treated as untrusted content throughout. Agent instructions are static constants; no retrieved text is interpolated into an instruction, and that property is asserted by test rather than by convention. Untrusted content reaches a model only as tool output.

Model Armor placement

BoundaryDispositionReasoning
Inbound analyst requestblockUntrusted user input at the system edge
Retrieved note contentflagDefence in depth; see below
Outbound customer messageblockThe only text that leaves the system

The middle disposition is a considered exception. A note containing an injection attempt also contains legitimate evidence — an instruction to disregard prior directives can sit in the same record as a factual account of an unanswered proposal. Blocking the record would discard the evidence in order to avoid the instruction. Because the architecture already confines retrieved text to the data channel, screening at this boundary is defence in depth rather than the control, and the correct disposition is to flag for the reviewer.

Validated against a seeded adversarial record: the injection matches the prompt-injection classifier at high confidence, a legitimate draft returns no match, and the investigating agent continues to extract and cite the record's factual content.

Memory scope

Memory informs the recommendation. It does not inform the diagnosis.

The investigation must remain attributable to the current snapshot, because that attributability is what makes deterministic verification possible. A recalled assertion is not a fabricated identifier the gate can resolve; it is prose originating in a prior session, against which the gate has no reference.

Memory is therefore bound to the action stage only, carries dispositions and stated preferences rather than risk assessments, and is rendered into the prompt beneath an explicit declaration that it must not be cited as evidence. Durable records requiring audit trails and tenant scoping belong in the case store; this is the soft-recall half alone.

7. Quality assurance

Three tiers, reported separately and never aggregated into a single figure.

TierMethodStanding
1 — deterministicSelection order, banding, rule firing. One correct answer exists.release gate
2 — mechanical groundingCitation resolution, action within permitted set, uncited claimsregression check
3 — managed autoraterGroundedness, action appropriateness, uncertainty handlingadvisory

Tier 1 is a genuine pass or fail: the deterministic layer has one correct output and any deviation blocks release. Tier 2 verifies that every claim resolves to a real record. Tier 3 applies the managed evaluation service rather than a locally reimplemented judge.

Rubric governance

Custom rubrics are versioned, and the version is recorded with every score so results are never compared across rubric revisions. Each rubric carries anchor cases executed on demand: against identical evidence, a correct disqualification scores 5, a further follow-up message scores 1, and a fabricated approval claim scores 1. A rubric never exercised against a known-poor answer is a rubric that may return a high score for anything.

Known limitation of the managed groundedness metric. It is a binary judgement rendered by a model and it is not deterministic: an identical diagnosis scored 0 and then 1 on consecutive executions minutes apart. It is also strict regarding literal attribution, marking a role descriptor unattributable where the evidence names only the individual. Groundedness means are therefore not reported as stable figures, and should not be used as an acceptance criterion without human adjudication.

The regression suite is hermetic by design and requires no model quota, so a transient provider error cannot produce a failing build. Tests requiring live model access are opt-in and separately marked.

Tuning. All rule thresholds, the review cap, the staleness tolerance and the model identifier are held in a single configuration module. Threshold changes take effect on the next run and require no code modification. Changing a threshold invalidates prior tier-1 expectations, which should be re-baselined in the same change.

10. Cost profile

Two components drive spend. The hosted runtime bills continuously while provisioned and is the dominant line item; it does not scale to zero. Model inference bills per invocation and is bounded architecturally rather than by convention — deterministic selection runs first and caps how many opportunities ever reach a model, at roughly 6,500 tokens per opportunity reviewed.

Screening and evaluation bill per call and are immaterial at review volumes. Storage and analytics are negligible. Scaling the opportunity population does not scale model cost, because the expensive stage only ever processes the capped review set.

A billing budget with staged alert thresholds is configured against the project.

11. Recommended before production operation

The following are known and deliberate scope boundaries for this release, listed in the order I would address them.

  1. Approval capture at the Gemini Enterprise surface. Approval is enforced at the operator interface. In the conversational surface a proposal is returned in a pending state with no mechanism to record the decision. Until a capture path exists, treat the conversational surface as read-only and record approvals through the operator interface.
  2. Post-write verification. Nothing currently reads back a system of record to confirm intended state, because nothing writes to one. Any write path added must be accompanied by read-back confirmation — a successful API call is not a completed workflow.
  3. Telemetry egress from the hosted runtime. Analytics and tracing are confirmed operating from the operator interface. Emission from the hosted runtime is not yet landing; identity grants and configuration propagation have been eliminated as causes, and egress from the runtime sandbox remains under investigation.
  4. Tenant and entitlement model. There is no per-seller entitlement enforcement. A multi-seller deployment requires that scoping before rollout.
  5. Currency and time-zone handling. Amounts are single-currency and dates are treated as calendar dates. A multi-region deployment requires currency on amount fields and tenant-aware day boundaries, since elapsed-day rules are otherwise ambiguous across zones.
  6. Threshold calibration. Current thresholds are reasoned starting positions, not empirically derived. Calibrate against closed outcomes over an operating quarter before treating band assignments as authoritative.
  7. Evaluation corpus. The present scenario set exercises behaviour; it is not large enough to support an accuracy claim. Establishing one requires a labelled corpus with analyst adjudication.
On reported performance. No accuracy, efficiency or financial-impact figure is asserted anywhere in this document or in the system's reporting. Operational metrics are generated from captured execution data; where a value was not captured it is reported as such.

12. Questions your team will ask

Architecture

Why two agents rather than one?

Measured rather than assumed. Against an identical case set, identical tooling and the same verification gate, a single agent matched the two-agent configuration on every objectively scoreable dimension at roughly two-thirds the cost. The split is retained for separation of concerns — the drafting prompt can be revised without touching the diagnostic prompt — but that is a maintainability argument, not a quality one. I would not defend it as a quality improvement on current evidence.

Why is the review set selected deterministically?

Because selection is arithmetic, and arithmetic delegated to a model introduces variance without adding capability. An earlier design submitted opportunity records directly to a model and asked which were at risk; identical inputs produced differing counts across runs. The underlying error was asking one component to serve as both the data layer and the reasoning layer.

Is the output reproducible?

In two parts. Triage is fully reproducible — the same snapshot yields the same review set in the same order on every execution, demonstrable with no model invoked. The recommended action is not deterministic, because it is a judgement with more than one defensible answer. That distinction is the boundary functioning as designed, and it is why the action set is closed and the output verified.

A model sits in the entry path on the conversational surface. Does that compromise the determinism claim?

It is the correct question to ask. The entry agent routes and presents; it cannot score an opportunity, alter the review set, or bypass verification, because those execute in fixed order within the tool it invokes. But a model is in the path, and that should be stated rather than glossed.

Correctness and control

How is fabrication prevented?

Eight deterministic checks execute after generation. Six block. The most consequential asserts that no quantity may appear in customer-facing text unless it appears in the source material supplied to the model. The source corpus is the union of everything the tools could return for that opportunity, so a figure the model did not read is a figure it produced.

Why verify generated prose rather than the structured output?

Because the structured fields are assembled in code and cannot fabricate, whereas the prose is what a reviewer reads and acts upon. A verification layer that validates only the safe artefact provides assurance without providing protection. This is a failure mode I have seen in production: a system whose integrity gate validated identifiers on a code-constructed object while the generated narrative — the part humans consumed — was never examined, and whose published performance figures did not reconcile with its own stored records.

What prevents a well-sourced but incorrect conclusion?

Nothing entirely, and the system does not claim otherwise. The gate resolves fabricated citations and unsupported quantities. It cannot resolve a conclusion that is correctly attributed and still wrong — a misread of tone, or a causal account the evidence merely permits. That residual is why human authorisation is mandatory and why counterevidence and unknowns are required fields rather than optional ones.

An adversarial record was cited as evidence. Is that a control failure?

No, that is correct behaviour. The record contains an injection attempt and legitimate factual content in the same body. Treating untrusted text as data means extracting the facts and disregarding the embedded instruction. Declining to read the record would discard evidence and would be the worse outcome.

Data and operations

Why batch ingestion rather than live CRM API reads?

Three reasons. It bounds load on the CRM org and removes API rate limits from the critical path. It makes every run reproducible against a known snapshot, which is a precondition for the deterministic layer being testable at all. And it makes freshness explicit rather than assumed — the extract timestamp is a first-class input, and elapsed-day rules are qualified against it.

What happens when a source is unavailable?

It degrades in three layers, each covered by tests that inject the failure. An unreadable source reports its state and carries an explicit instruction that absent records are not evidence. Model errors receive one retry when transient and none when they indicate a defect. A failed stage downgrades the result and names the stage that failed. No stage output is ever substituted with generated content.

How does this scale?

The deterministic layer is relational and moves to the warehouse the extract already lands in. The model stage is the constrained resource, and it is bounded by design: selection precedes it and caps the set. Opportunity volume therefore drives warehouse cost, not model cost.

How do we operate this day to day?

Thresholds, the review cap and the staleness tolerance are configuration in a single module; changes take effect on the next run. The regression suite is hermetic and gates changes without model quota. Every execution is correlated end to end by a single identifier, and operational reporting is generated from captured data rather than authored.

Governance

Where is memory used, and where is it deliberately not?

Memory carries seller dispositions and stated preferences, and reaches the action stage only. It is excluded from the diagnostic stage on purpose: the investigation must remain attributable to the current snapshot, or deterministic verification has no reference against which to resolve a recalled assertion. Durable records requiring audit trails belong in the case store, not in soft recall. A remembered risk label is not current evidence.

Why Model Armor rather than the agent security tooling?

Placement and cost. Model Armor screens at the three boundaries this system actually has, with different dispositions at each. The security dashboard operates through Security Command Center, whose commercial tiers are an organisational commitment disproportionate to a single workload. Screening is also positioned as defence in depth, not as the primary control — the architectural containment of untrusted text is the control.

The agents scored maximum marks on the quality rubrics. Should we be sceptical?

You should, and the rubrics are instrumented for exactly that. Anchor cases execute on demand: against identical evidence the same rubric awards a low score to a redundant follow-up and to a fabricated approval claim. That establishes the rubric discriminates, which makes a high score a result rather than an artefact. Separately, the managed groundedness metric disagreed with itself across consecutive executions, so its mean is not reported as a stable figure anywhere.

What is the weakest part of this system?

The evaluation corpus. It exercises behaviour but is not large enough to distinguish architectural variants or support an accuracy claim — I know this because the architectural comparison I ran returned an inconclusive result. Second is approval capture at the conversational surface, which is enforced at the operator interface and not yet at the other.

What governed what you chose not to build?

One rule: a capability is not adopted because the platform offers it. Autonomous writes, tenant modelling, a bespoke interface, retrieval augmentation and forecasting were all scoped out deliberately, and each is recorded as a boundary rather than an omission. The same rule applied to managed services — one was evaluated and declined on the basis of its own documentation.
